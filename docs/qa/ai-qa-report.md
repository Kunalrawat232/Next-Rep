# AI-assisted QA report

How AI contributed to QA and how its output was validated. The counts below are updated after each AI-assisted testing task; nothing is merged without the developer's review. Counts are as recorded at the time in the [AI log](../learning/ai-log.md); where the "Kept" or "Rejected" column says "not recorded", the log did not record how many tests were kept or rejected one by one.

## Method

1. The `qa-tester` agent and the `parser-test-cases` skill propose edge cases, negative tests and failure scenarios, then write them as Vitest tests.
2. Every generated test is run and every failure is triaged: a real bug is fixed, a wrong expectation is corrected (see the notes per task). How many tests were kept or rejected one by one was not recorded.
3. New tests must be shown to fail without the feature (or against a deliberately broken version) so they can actually catch regressions.
4. Suspected bugs are reported, not silently fixed; the developer decides which are valid.
5. Exploratory checks were done with Claude in Chrome on the running app (2026-10-17 to 2026-10-19, desktop width and phone-sized frames): the workout journey, the coach and its second provider, charts, History and the empty-workout rule. Offline testing with Playwright MCP was not done (the Playwright e2e spec covers log offline, then sync).
6. `code-reviewer`, `security-auditor`, the `code-review` plugin and `pr-review-toolkit` review each feature's diff; findings are triaged by the developer.
