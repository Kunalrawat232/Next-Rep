# Data model (Supabase / Postgres)

There are 8 tables (counted from migrations 0001 to 0005), all with **RLS enabled**. All have `user_id uuid references auth.users not null`, except `profiles` (keyed by `id`, which is the auth user id), `api_daily_totals` (a project-wide counter, no `user_id`) and the shared exercise catalogue (`user_id` is null for global rows). Timestamps are `timestamptz`. Schema changes go in `supabase/migrations/` as numbered SQL files, never edited only in the dashboard.

## RLS policies

- `exercises`: everyone signed in can `select` rows where `user_id is null` (global) or `user_id = auth.uid()`; insert/update/delete only own rows.
- All other tables: `select`, `insert`, `update`, `delete` only where `user_id = auth.uid()`; `insert` and `update` also check `user_id = auth.uid()` (`WITH CHECK`) so a row cannot be reassigned to another user.
- Policies use `to authenticated` plus the ownership predicate, written as `(select auth.uid()) = user_id`.
- No `SECURITY DEFINER` function is used to work around permissions. The exceptions are the rate-limit functions `consume_rate_limit` (two-argument and legacy one-argument versions) and `consume_daily_ceiling`, which are deliberate (see Integrity beyond RLS).
- Write an automated test proving user A cannot read or write user B's rows. This is a key security demo point.

## Integrity beyond RLS

- **Composite foreign keys.** `gyms`, `workouts` have `unique (id, user_id)`, and child rows reference `(parent_id, user_id)`: `gym_bars` → `gyms`, `workouts.gym_id` → `gyms`, `sets.workout_id` → `workouts`. Foreign keys bypass RLS, so without this a user could attach their rows to another user's gym or workout.
- **Exercise visibility trigger.** `sets_check_exercise_visible` (SECURITY INVOKER, so subject to the `exercises` policies) rejects a set that points at an exercise the user cannot see, for example another user's custom exercise.
- **Rate limit functions.** All `SECURITY DEFINER` functions are: `consume_rate_limit(p_scope text, p_window_seconds int)`, a legacy one-argument `consume_rate_limit(p_window_seconds int)` that counts as scope `parse` (kept for a `/api/parse` deployed before migration 0005), and `consume_daily_ceiling(p_scope text)`. They are `SECURITY DEFINER` on purpose: clients must not be able to write the counter tables directly (they could reset their own limit). `consume_rate_limit` touches only the caller's own row, checks `auth.uid()`, pins `search_path`, validates its arguments (scope is 1 to 20 lowercase letters, window 1 to 3600 seconds), is not executable by `anon`, and returns the caller's request count for the current window and scope. `/api/parse` (scope `parse`) and `/api/coach` (scope `coach`) both call it and compare the count to their own limits (`api/_lib/supabase.ts`; numbers in [API contracts](api-contracts.md)). `consume_daily_ceiling('gemini')` counts one model call in `api_daily_totals`, returns whether the project is still under the fixed ceiling, and turns an account away after 100 calls an hour without counting it; both endpoints call it. Trade-off: they live in `public` (the exposed schema) so they can be called through the API. `sets_check_exercise_visible` is the only other function and is `SECURITY INVOKER`.
- **Seed id squatting.** Seed exercise ids are public and clients may choose their own exercise ids (offline creation), so a user could pre-create a row with a seed id. The seed therefore resets `user_id` to null on conflict, reclaiming the id as a global exercise. Covered by a regression check.
- **Profiles** are created by the client on first sign-in (an upsert allowed by the `profiles` policies), not by a trigger on `auth.users`, which would need another `SECURITY DEFINER` function.

## Constraints

- Check constraints on reps and weights repeat the validator ranges (values in [weight rules](../domain/weight-rules.md), source `src/domain/validation/config.ts`), plus sensible length limits on text columns.
- `sets.id` and `workouts.id` are primary keys used for idempotent upserts.
- Index on `(user_id, exercise_id, logged_at desc)` for history and charts; every foreign key is indexed.
- `sets`: `total_kg = bar_kg + 2 × per_side_kg` whenever both are present, and `input_mode = 'per_side'` requires both. **Editing a set's weight must update `total_kg`, `bar_kg`, `per_side_kg` and `input_mode` together**, otherwise the database rejects it.
- `exercises.muscle` is one of 16 muscle groups (check constraint, mirrored by `src/domain/exercises/muscles.ts`) or null. About 890 global exercises are seeded: curated ones with voice aliases plus imported ones (the counts are in the two seed JSON files under `src/domain/`; [ADR-010](decisions/010-exercise-library-and-muscle-search.md)).
- One gym per user (unique index on `user_id`, [ADR-015](decisions/015-one-gym-per-user.md)); exercise names unique per owner, case-insensitive.
- `gym_bars`: at most one `ez_bar` and one `smith` per gym (partial unique index), bar names unique per gym ignoring case. The barbell is `gyms.default_bar_kg`, not a `gym_bars` row. A logged exercise finds its bar by equipment: barbell, then the gym's barbell weight; EZ bar and Smith, then the bar of that `kind`; `other` bars are manual overrides only ([ADR-009](decisions/009-gym-bars-and-default-gym.md)).
- Data API privileges: `anon` has none; `authenticated` gets table privileges and RLS decides rows; `api_rate_limits` has no direct privileges; `api_daily_totals` has RLS enabled and no policies, so clients cannot read or write it.

## Notes

- The weight convention is described in [weight rules](../domain/weight-rules.md); `total_kg` is the only value charts, PRs and suggestions use.
- `raw_transcript` is synced (confirmed default); revisit for privacy before submission.
