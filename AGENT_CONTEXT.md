# AGENT_CONTEXT.md

A knowledge base for AI agents working on Next Rep. **Start from [agent_docs/index.md](agent_docs/index.md):** the detailed knowledge for the local-first log and sync, the workout screens, the API and the coach, the database and testing now lives there, one folder per area. This file keeps what is shared: the overview, the folder map, the frontend (routes, hooks, components), auth, domain logic, configuration, conventions and the state of the work. Where a section below says "Moved to", read that doc instead. Things that could not be verified from the code are marked **unverified**. If the code and a doc disagree, the code wins: fix the doc.

## 1. Overview

**Next Rep** is a voice-first gym workout logger, shipped as an installable PWA (React single-page app, Supabase backend, Vercel hosting). Built solo for the Build With AI Hackathon 2026 (feature freeze 25 Oct 2026, submit 30 Oct 2026; judging weights: AI practice 35%, engineering 30%, product 25%, idea 10%).

**Principle: "AI listens, code verifies."** Speech recognition and Gemini are untrusted input; every number that reaches storage passes the deterministic validator (`src/domain/validation`) and is shown to the user first.

**Who it is for:** someone lifting between sets, one hand free, often with no signal in the gym basement. Offline logging is a core requirement.

### How data flows

```
Screen (features/*)
  ├─ gyms, exercises, auth ──> service interface (GymService, ExerciseService, AuthService)
  │                            └─> src/data/remote/* ──> Supabase (RLS)
  └─ workouts and sets ─────> LogStore (src/data/local, Dexie, one DB per user)
                               └─> SyncScheduler ─> SyncWorker ─> RemoteLog.upsertWorkouts/upsertSets/softDeleteSet ─> Supabase
                               └─> after each push pass, pullHistory ─> RemoteLog.fetchWorkouts/fetchSets ─> LogStore.mergePulled
Screens read the LogStore through hooks that re-read when `useSyncStatus()` changes (pending, failed, syncing, pulledVersion).
```

Gym and exercise data is online-first with a device copy for offline use: the gym list is saved to the Dexie `gymCache` table on each load, and each workout stores a local-only `gymSnapshot` (name, bars) so logging works offline.

## 6. Auth and user data

- **Method:** email + password through Supabase Auth (ADR-007). Sign-up with "Confirm email" off means no confirmation step today; the dashboard settings still to switch on are in section 12.
- **Session:** supabase-js stores it in local storage under `next-rep-auth` and refreshes the token. The app reads the signed-in user from that stored session at start (`readStoredUser`) so an offline start does not wait for a refresh. The real token is checked by the server on every request (RLS).
- **Sign-out** is `scope: 'local'` (works offline; the refresh token stays valid on the server, a known trade-off).
- **Scoping:** every row has `user_id`; RLS lets a user read and write only their own rows; global exercises (`user_id` null) are readable by everyone. Composite foreign keys stop a row pointing at another user's gym or workout. The device database is per user (`next-rep-<userId>`), and `SyncProvider` is keyed by user id.
- **Sign-out and the device:** on sign-out, `purgeSynced` clears synced rows and the gym cache; rows still waiting to sync stay (the user is warned first and must choose "Sign out anyway"). Retained-data caveats are in `docs/security/threat-model.md`.
- `ProtectedRoute` sends signed-out visitors to `/sign-in` and back.

| Parse result shape     | `parser/schema.ts` `ParseResultSchema`                                                                               | intent, exerciseId, weight {value, unit, mode}, reps, confidence, issues, rawTranscript, source (`parser` or `gemini`). Produced by `parseTranscript(text, { exercises, unit, currentExerciseId? })` in `parser/index.ts`; `needsFallback(result)` says when Gemini should be asked.                                                                                                                                                                                                                                                                                                |
| Voice drafts           | `features/voice/` (`useSpeech`, `speech.ts`, `voiceDraft.ts`)                                                        | `draftFromParse(parse, {exercises, gym, unit})` returns `set` / `repeat` / `undo` / `edit` / `rest` / `unclear`. A `set` is a `SetCandidate` with `source: 'voice'`, the spoken weight and the gym bar; `validateSet` runs on the confirm card. With no per-side or total word the validator reads a bar weight as a total (it asks only below the bar or after a big jump), and the card has a Total / Per side toggle. `repeatDraft` copies the last set's stored total as a total.                                                                                               |
| Voice parser           | `parser/` (`parse.ts` flow, `numbers.ts`, `exercise.ts`, `quantities.ts`, `intent.ts`, `vocabulary.ts`, `config.ts`) | Pure. Reports the weight and unit AS SPOKEN (no conversion; no unit means the user's unit), mode `per_side`/`total`/`unspecified`. A set needs a number, and an exercise or a unit or rep word. Issues (`issues.ts`): NO_EXERCISE, NO_WEIGHT, NO_REPS, AMBIGUOUS_WEIGHT_MODE, LOW_EXERCISE_MATCH, UNKNOWN_EXERCISE_WORDS, EXTRA_NUMBER, UNRECOGNISED_WORDS, SUSPICIOUS_INPUT, TOO_LONG, NO_SPEECH, PARSE_FAILED. `needsFallback`: confidence under 0.8, never for injection, over-long or empty text. Commands (undo, rest, same, make) are read only from the start of the phrase. |

**`validateSet` details:** `SetCandidate` = `{equipment, weight: {value, unit, mode: total|per_side|unspecified}, reps, barKg, source?: 'tap'|'voice'}` (source defaults to voice, the safe side). Checks reps 1-100, weight 0-500, per side 0-250; a total below the bar asks "total or per side?"; a total more than 40% (`jumpFraction`) from the last session asks (a tapped jump with no other reading is only a warning); "Did you mean 60?" for 13/30 ... 19/90 confusions is **voice only**; weights not a multiple of 1.25 kg per side get a soft `PLATE_INCREMENT` warning; equipment without a bar ignores per-side input with `PER_SIDE_IGNORED`. Every resolved weight is storable (satisfies the DB checks).

**Personal records:** a set is a record when it beats the sets before it of the same exercise (ordered by `loggedAt`, then `id`): `weight` if strictly heavier than all earlier sets; `reps` if more reps than any earlier set at exactly that weight (needs an earlier set at that weight). First set never; 0 kg never a weight PR; one kind per set; weights compared in hundredths. Computed on read from the sets on the device. **Known limit:** after sign-out clears synced sets, records see only what is on the device until the pull restores history.

**Sync rules:** moved to [agent_docs/local-data/sync-worker-and-pull.md](agent_docs/local-data/sync-worker-and-pull.md) and [empty-workouts.md](agent_docs/local-data/empty-workouts.md).

## 10. Conventions

- **Naming:** React components `PascalCase.tsx`; hooks `useThing.ts`; domain modules are `folder/index.ts` with the tests beside them; Postgres columns `snake_case`, TypeScript `camelCase` (mapping is in `src/data/remote/*.ts`).
- **Files:** one feature per folder under `src/features/`, exporting through its `index.ts`. Do not export pages that import heavy libraries from a barrel that is imported elsewhere (the progress barrel exports only `PrBadge` and `useRecordMarksState` so Recharts stays in a lazy chunk).
- **Formatting:** Prettier (`npm run format`); it rewraps long lines. ESLint flat config; no `any`.
- **Commits:** one finished task = one commit: a single short Conventional Commit subject line, no body, plus the Co-Authored-By attribution trailer when the harness asks for one (the trailer is the only allowed body). Ask before any other commit. Never push without approval. If the user says they handle git themselves, do not commit. Each feature is built on its own branch (`feat/gyms`, `feat/exercises`, `feat/local-sync`, `feat/workout-screens`, `feat/history`, `feat/progress`, `feat/pull-history`, and later `feat/home`, `feat/liquid-glass` and `feat/coach`) and merged into `main` with a merge commit (no squash, so stacked branches stay mergeable). All of these are merged into `main`; `main` and 12 other branches were pushed and CI is green on `main`. Some merged branches exist only locally (`feat/coach`, `feat/home`, `feat/liquid-glass`, `feat/settings`, `feat/units`, `fix/double-tap-guards`, `refactor/shared-ui`).
- **Docs map:** `docs/product` (problem, requirements, journeys, open questions), `docs/architecture` (overview, tech-stack, offline-sync, data-model, api-contracts, `decisions/001-018` ADRs), `docs/domain` (weight-rules, voice-grammar, glossary), `docs/standards` (working agreement, coding standards, testing strategy), `docs/design` (design system, screens, workflow, handoff exports), `docs/security` (checklist, threat model), `docs/ai` (agents, guardrails, Gemini prompts, lifecycle map), `docs/delivery`, `docs/qa`, `docs/hackathon`, `docs/plans/roadmap.md`, `docs/learning/ai-log.md` (one entry per finished feature) and `lessons.md`.

## 11. How to extend

**New exercise field, or a new table or column the app syncs:** see [agent_docs/database/schema-and-rls.md](agent_docs/database/schema-and-rls.md) ("Adding to the schema"). Ask the developer first: it changes the data model.

**New page:** create `src/features/<name>/<Name>Page.tsx` (+ hooks), export it from the feature's `index.ts` (or use a `lazy` route if it pulls a heavy library), add the route in `src/app/routes.tsx`, add a nav item in `src/components/AppShell.tsx` if needed (and remove it from the "not a link yet" test list in `AppShell.test.tsx`), give it loading, empty and error states, write whole-app tests with `renderApp`, and update `docs/design/screens.md` and the relevant `agent_docs` doc.

**New Vercel endpoint:** see [agent_docs/api/functions-and-handlers.md](agent_docs/api/functions-and-handlers.md).

**New domain rule:** pure function in `src/domain/<area>/index.ts`, table-driven tests beside it in the same task, thresholds in a config object, document in `docs/domain/weight-rules.md`.

**New environment variable:** add the name (no value) to `.env.example`, validate it in one place (`src/data/remote/env.ts` for browser variables; never use a `VITE_` prefix for a secret), and add it to the table in section 8.

### Known limits and tech debt

| Item                                                   | Detail                                                                                                                                                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Pull is a full read                                    | No `updated_at` on workouts, so the pull reads all finished workouts and sets each app start (500 per page, by id, ending on an empty page). Fine at this scale; an incremental pull needs a migration. |
| Pulled workouts have no bars unless the gym was cached | `gymSnapshot` is filled from `gymCache`; otherwise the workout has no snapshot and bar exercises ask for the bar.                                                                                       |

### Decisions and why (more in `docs/architecture/decisions/`)

- ADR-002: logged weight is the total including the bar, so history and PRs compare like with like; dumbbells are per dumbbell.
- ADR-003: Gemini only as a fallback behind `/api/parse`; its output goes through the same validators.
- ADR-007: Supabase session read locally at start; email + password.
- ADR-008: design tokens and theming (dark default).
- ADR-009: gym bars have a `kind` so exercises find their bar.
- ADR-018: the coach asks a second free provider (Groq, any OpenAI-style endpoint, `api/_lib/fallbackProvider.ts`) when Gemini fails, cannot be read, or its day of calls is used up; it is not Grok, because no free xAI tier could be confirmed.
- ADR-017: a text-only AI coach on the Gemini free tier (`/api/coach`, `COACH_MODEL`); read only; the chat stays on the device (Dexie version 3, `coachMessages`); a small anonymous summary of recent training is sent if the person allows it.
- ADR-016: CSS glass tokens and an ambient colour layer for the whole UI; liquid-gl lenses on the floating tab bar, the Workout button and the sticky rest pill (`useLiquidGlass(ref, preset)`), behind a Settings switch.
- ADR-015: one gym per user (unique index, migration 0004); no list, name, default or delete; the first workout creates it with a standard barbell.
- ADR-010: exercise library is 56 curated plus about 836 imported (dataset text is MIT); search ranks curated before imported.
- ADR-013: exercise demonstration GIFs are hotlinked from the dataset (jsDelivr, pinned commit), never stored or cached; © Gym visual, non-commercial, credited in the README, THIRD_PARTY_NOTICES.md and the About page (`/about`, linked from Settings); one switch turns them off.
- ADR-014 (accepted): the popular exercises show free-exercise-db photos crossfaded start to end (sharper, smoother than the 12-frame GIFs); GIFs stay as the fallback.
- ADR-011: local-first log with a sync worker (create-and-end offline, deletes of saved sets need internet; failures classified by cause so outages never fail rows).
- Tapped weights are not second-guessed by "Did you mean" (voice only); the validator takes a `source`.
- Volume was left out until dumbbell doubling is decided.
- Progress and PR badges are computed on read, never stored, so undo fixes them.
